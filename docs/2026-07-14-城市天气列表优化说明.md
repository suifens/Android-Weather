# 首页城市天气列表优化说明

**日期**：2026-07-14  
**范围**：首页城市天气列表及相关基础设施重构  
**目标**：保证城市排序可靠、减少无效刷新、拆分臃肿职责、清理历史债务

---

## 1. 背景

优化前，首页「城市天气」相关实现存在几类问题：

| 问题 | 表现 |
|------|------|
| 排序不可靠 | 城市顺序依赖 SQLite 行序 + 删表重插，无显式 `sortOrder` |
| 刷新通路混乱 | `LiveData` 与 EventBus `cityChanged` 双通道，易竞态 |
| 性能开销大 | `weatherMap` 全量广播、多 Tab 同时拉网、Adapter 全量刷新 |
| ViewPager 脆弱 | 预创建 Fragment 列表，结构变更时整页重建成本高 |
| 架构臃肿 | `MainViewModel` 同时管城市、天气、定位、背景图等 |
| 历史死代码 | `HomeFragment` / `WeatherActivity` 等与主路径重复 |

因此按优先级分多轮落地改造。

---

## 2. 修改总览

### 2.1 数据层：城市排序与仓库拆分

**改了什么**

- `CityEntity` 增加 `sortOrder`
- 用户库 `AppDatabase`：`version 2 → 3`，迁移补齐 `sortOrder`
- 搜索资产库 `CityDatabase`：补 `sortOrder` 列，避免 Room 校验失败
- `CityDao`：`ORDER BY sortOrder`；排序用 `@Transaction` + `UPDATE`
- 新增 `CityRepository`：用户城市 CRUD / 排序
- 新增 `WeatherRepository`：天气 HTTP、Room 缓存、内存快照
- 新增 `LocationRepository`：LOST 定位 + Geocoder + cityCode 解析
- 新增 `WeatherBgRepository`：天气/日历背景拉取、落库、内存缓存
- 新增 `CityListLogic` / `CacheCodec`：可单测的纯逻辑

**为什么改**

- 排序是用户可感知的正确性问题；靠「删库重插赌行序」不稳定  
- `MainViewModel` 职责过多，难测、难改；仓库拆分后 UI 只做编排  
- 纯逻辑抽出后便于 JVM 单测，不依赖 Android 环境

---

### 2.2 刷新通路：去掉城市变更 EventBus

**改了什么**

- 添加 / 删除 / 排序成功后：写库 → `awaitCitiesCacheRefresh(forcePost=true)`
- 首页 / 城市列表只观察 `mainViewModel.cities`
- 删除 `MessageEvent`；去广告改为 `AdRemovalManager.adRemovalChanged`
- `app/build.gradle` 移除 EventBus 依赖
- 清理 `WeatherSpUtils` / `WXEntryActivity` / `PushMessageReceiver` 中注释掉的 EventBus 代码

**为什么改**

- 城市列表已有 LiveData，再靠 EventBus 强制刷新说明状态同步不可靠  
- 双通道容易出现「跳过 post → observe 不跑 → loading 关不掉」  
- EventBus 与生命周期弱绑定，长期维护成本高

---

### 2.3 性能：按城分发天气 + Tab 懒加载

**改了什么**

- 新增 `CityWeatherUpdate` + `weatherUpdate` LiveData  
  - 单城天气变更只通知该城，不再每次 `postValue(整份 HashMap)`
- 新增 `weatherRefreshWindow`（当前 Tab ±1）
- `WeatherViewModel` 拆分：
  - `loadCacheDisplayOnly()`：只读缓存展示
  - `loadCache()`：缓存 + 过期再请求网络
- `WeatherFragment`：`onStart` 只展示缓存；进入刷新窗口才拉网
- 城市列表预加载：启动时从 Room 把各城缓存灌进内存

**为什么改**

- 多城时全量广播会让所有 Tab / 列表同时刷新，浪费 CPU  
- 离屏 Fragment 在 `onStart` 就打网络，弱网下并发请求过多  
- 用户通常只关心当前页和左右相邻页

---

### 2.4 ViewPager：cityId 驱动

**改了什么**

- 新增 `WeatherPagerAdapter`
  - `createFragment(position)` 按 cityId 创建
  - `getItemId` / `containsItem` 稳定标识
- `MainFragment` 不再预创建并持有一堆 `WeatherFragment` 实例
- 末尾加城：`appendCity`；结构变化：`submitCityIds`
- `offscreenPageLimit`：首页与城市列表卡片模式均收敛为 `2`

**为什么改**

- 预创建 Fragment 列表不符合 ViewPager2 设计，删/排时易错乱  
- 稳定 itemId 减少无意义重建，滑动更平滑

---

### 2.5 列表 UI：DiffUtil + 生命周期安全协程

**改了什么**

- `CityListAdapter`：`ListAdapter` + DiffUtil；背景图 Job 随 ViewHolder 取消  
- `CityManagerAdapter`：`submitList` 走 DiffUtil；删除用 `notifyItemRemoved`  
- `WeatherItemFragment`：用 `viewLifecycleOwner.lifecycleScope`  
- 关闭 `AppDatabase.allowMainThreadQueries()`

**为什么改**

- `notifyDataSetChanged` 粗暴、易闪烁  
- Adapter 内裸 `CoroutineScope` 可能泄漏或错绑回收后的 Holder  
- 主线程查库有 ANR 风险

---

### 2.6 缓存存储：Java 序列化 → JSON

**改了什么**

- `CacheCodec`：写入 `JSON1|{type,payload}`  
- 读取优先 JSON；失败再回退 Java `ObjectInputStream`（兼容旧缓存）

**为什么改**

- Java 序列化体积大、类结构一变易坏、调试困难  
- Gson 与现有 `WeatherBean` 等注解体系更契合  
- 兼容旧数据，避免升级后白屏

---

### 2.7 清理死路径

**删除**

- `WeatherActivity` / `HomeFragment` / `HomeItemFragment` / `WeatherItemViewModel`
- 对应布局 `activity_weather.xml` / `fragment_home.xml`
- Manifest 中的 `WeatherActivity` 声明

**为什么改**

- 主入口早已是 `MainActivity` → `MainFragment`  
- 重复实现增加认知成本与误改风险

## 4. 当前数据流（改造后）

```text
Room(city + cache)
    ↑↓
CityRepository / WeatherRepository / LocationRepository / WeatherBgRepository
    ↑↓
MainViewModel（编排：cities / weatherUpdate / weatherRefreshWindow / curLocation）
    ↑↓
MainFragment (WeatherPagerAdapter)
    → WeatherFragment × N（当前±1 才拉网）
CityListActivity（网格订阅 weatherUpdate 局部刷新）
CityManagerActivity（排序 UPDATE，完成后 force 刷新 cities）
```

## 5. 建议自测清单

1. **添加城市**：新 Tab 出现、自动选中新城市、天气能出  
2. **拖拽排序 / 删除**：杀进程重进后顺序仍正确；定位城保持首位  
3. **滑动多城**：较远 Tab 不应频繁发网络；切到该 Tab 再刷新  
4. **城市列表网格**：单城天气更新时局部刷新，不必整表闪烁  
5. **去广告**：领取成功后首页广告隐藏（LiveData，非 EventBus）  
6. **冷启动**：定位城与缓存天气正常展示；升级后旧缓存可被兼容读取  

单测：

```bash
./gradlew :app:testXiaomiDebugUnitTest --tests "com.chunjing.tq.db.*"
```

## 6. 未做 / 可后续继续

- 背景图拉取以外，`MainViewModel` 仍有版本检查、鸡汤、定时定位等，可继续薄化  
- `CityListActivity` 卡片 Pager 仍偏重「全量重建 Fragment」  
- 缓存全量迁 JSON 后，可择机清理极老的 Java 序列化回退路径  
- `WeatherViewModel` 对 `MainViewModel` 的委托可进一步改为直接依赖 `WeatherRepository`

---

## 7. 一句话结论

这次改造把首页城市天气从「EventBus + 全量广播 + 删库赌顺序」推进到「显式 `sortOrder` + LiveData 单源 + 按城更新 + Tab 懒加载 + 仓库分层」，在正确性和性能上都针对多城市场景做了加固，并为后续演进留出可测、可拆的边界。
